## 资源分配图与等待图

- `进程 → 资源`：请求边。
- `资源 → 进程`：分配边。
- 等待图中 `Pi → Pj`：Pi 等待 Pj 释放资源。
- 每类资源单实例：图中有环即可判定死锁。
- 多实例：无环一定无死锁；有环只表示可能死锁，需进一步检测。
- 普通等待链不是死锁；必须闭合成环。阻塞进程无法靠增加 CPU 时间片解除资源等待。

> 进程指资源是请求，资源指进程是分配；单实例见环即死锁，多实例见环再分析。

## 多实例资源检测算法

- `Available`：当前可用资源。
- `Allocation[i]`：Pi 已经持有的资源。
- `Request[i]`：Pi 当前实际等待的资源。
- `Work`：模拟可用资源。
- `Finish[i]`：Pi 是否可模拟完成。

```text
Work = Available
反复寻找 Finish[i]==false 且 Request[i]<=Work 的 Pi
找到后：
    Work = Work + Allocation[i]
    Finish[i] = true
```

最终所有 `Finish=true`，则当前没有死锁；最终仍为 `false` 的进程构成死锁集合。

> 拿 Work 满足当前 Request，完成后只归还 Allocation；暂时不满足先跳过，Work 增大后重新扫描。

## 与银行家算法的区别

| 项目 | 银行家算法 | 死锁检测 |
| --- | --- | --- |
| 目的 | 避免将来进入不安全状态 | 检查当前是否已经死锁 |
| 比较 | `Need <= Work` | `Request <= Work` |
| 找不到序列 | 不安全，不等于已死锁 | 剩余 Finish=false 的进程已死锁 |
| 时点 | 分配前安全检查 | 允许分配后定期检测 |

`Need=Max-Allocation` 表示未来最多还可能需要多少；`Request` 表示此刻真实等待多少。

检测策略允许死锁暂时发生。发现死锁属于检测；终止进程、剥夺资源或回滚属于解除。

## 个人易错点

1. 单个进程 `Request>Work` 只表示暂时不能完成，不等于已死锁。
2. 暂时不满足时应跳过并继续检查；其他进程释放资源后必须重新扫描。
3. 检测用当前 `Request`，不能拿未来 `Need` 代替。
4. 完成后加回已持有的 `Allocation`，不是未取得的 `Request`。
5. “允许死锁后再检测”是合法策略，不等于预防或避免。

## 死锁解除方法

检测只负责找出死锁；终止进程、资源剥夺和回滚才属于解除。

### 终止进程

- 可以一次终止全部死锁进程，处理简单但损失大。
- 也可逐个终止并重新检测，直到死锁消失。
- 选择牺牲者时考虑优先级、已运行时间、剩余时间、资源占用量、重做代价及历史回滚次数。
- 目标是以较小代价破坏死锁环。

### 资源剥夺

从死锁进程手中强制收回资源并交给其他进程。需要解决：

1. 选择哪个进程和资源作为牺牲者；
2. 将被剥夺进程恢复到一致检查点；
3. 防止同一进程被反复选择而饥饿。

并非所有资源都适合剥夺。CPU 状态、可重新装入的内存页较易恢复；已经发生的打印输出等物理副作用很难撤销。

### 回滚

回滚不是保存当前断点后继续，而是撤销不一致修改，退回此前保存的一致检查点，再重新执行。

例如转账处于“A 已扣款、B 未入账”时，不能保留该中间状态等待续跑；应撤销扣款并恢复到转账开始前。若没有检查点或事务日志，可能只能终止进程、从头执行，甚至人工修复数据。

> 终止是舍进程，剥夺是抢资源，回滚是退状态；每处理一次都要重新检测。

> 回滚不是记住做到哪里，而是退回仍然正确的状态。
