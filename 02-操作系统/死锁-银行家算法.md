## 一、核心数据

| 数据 | 含义 |
| --- | --- |
| `Available` | 当前可用资源向量 |
| `Max` | 进程声明的最大资源需求 |
| `Allocation` | 已分配给进程的资源 |
| `Need` | 进程最多还可能需要的资源 |

```text
Need = Max - Allocation
```

## 二、安全性检查

1. 初始化 `Work=Available`，所有 `Finish[i]=false`。
2. 寻找尚未完成且满足 `Need[i]≤Work` 的进程。
3. 假设该进程完成并释放已占有资源：`Work=Work+Allocation[i]`。
4. 重复寻找；所有进程都能完成则存在安全序列，否则状态不安全。

向量比较要求每一种资源都满足。比较的是 `Need≤Work`，不是 `Max≤Work`。

进程完成后加的是 `Allocation`。它临时取得的 `Need` 在完成时同时归还，净增加来自它原先占有的资源。

## 三、安全、不安全与死锁

- 安全：存在一个保证所有进程完成的安全序列。
- 不安全：无法保证未来一定完成，存在走向死锁的申请方式。
- 死锁：相关进程当前已经因资源形成无法解除的等待关系。

进程即使处于不安全状态，只要没有申请新资源并阻塞，仍可执行普通计算。CPU 调度只决定哪个就绪进程运行，不能凭空增加资源。

> 不安全是未来可能走进死胡同；死锁是现在已经困在死胡同。

## 四、选择题技巧

1. 先计算全部 `Need`。
2. 检查每个选项的首进程，若 `Need≰Work` 可立即排除。
3. 每通过一个进程就更新 `Work+=Allocation`。
4. 安全序列可能不唯一，逐项验证题目要求的候选序列。

## 五、个人记忆点

- **#N103｜公式**：`Need=Max-Allocation`。
- **#N104｜判据**：安全性检查比较 `Need≤Work`，并且每一类资源都必须满足。
- **#N105｜回收**：进程完成后执行 `Work+=Allocation`，不是加 `Need`。

## 七、资源请求算法

进程提出 `Request[i]` 后依次执行：

1. 检查 `Request≤Need`；不满足表示超过最大需求声明，属于错误请求。
2. 检查 `Request≤Available`；不满足表示库存不足，进程等待。
3. 两项都满足时进行试分配：
   - `Available-=Request`
   - `Allocation[i]+=Request`
   - `Need[i]-=Request`
4. 使用试分配后的 `Available` 初始化 `Work`，执行安全性检查。
5. 安全则正式批准；不安全则回滚三组数据并让进程等待。

> 先查声明，再查库存；假装借出，检查安全；安全成交，不安全回滚。

### 三种不能批准的情况

| 情况 | 处理 |
| --- | --- |
| `Request≰Need` | 错误请求，不进入试分配 |
| `Request≰Available` | 当前资源不足，等待 |
| 前两项满足但试分配后不安全 | 回滚，等待 |

“库存足够”和“请求合法”是两个独立判断。前置检查通过只表示可以试分配，不表示可以正式批准。

## 八、资源请求个人记忆点

- **#N109｜双检查**：先比较 `Request≤Need`，再比较 `Request≤Available`。
- **#N110｜试分配**：前两项通过仍不能直接批准，必须先修改三组数据并做安全性检查。
- **#N111｜新 Work**：安全检查的初始 `Work` 必须使用试分配后的 `Available`，否则会把已借出的资源重复计算。
- **#N112｜回滚**：试分配不安全时，同时恢复 `Available`、`Allocation`、`Need`，进程等待而非终止。
- **#N113｜分类**：超过 `Need` 是错误请求；超过 `Available` 是库存不足。
