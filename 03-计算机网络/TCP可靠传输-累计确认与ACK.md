# TCP 可靠传输：累计确认与 ACK

## 定义

TCP 确认号 `ack` 表示：**接收方下一步期望收到的对方字节序号**。

因此，`ack=N` 可以直接理解为：`N-1` 及以前的字节已经连续收到，当前下一步等待 `N`。

## 核心规则

### 1. ack 指向“下一个期望序号”

若收到对方一个 TCP 报文段：

- `seq=S`
- 携带 `L` 字节数据
- 中间没有缺口

则数据范围为 `S ~ S+L-1`，确认号可推进到：

`ack = S + L`

例如 `seq=3000`、长度 `400B`：数据覆盖 `3000~3399`，完整收到后返回 `ack=3400`。

### 2. seq 与 ack 属于两个方向

- `seq`：本方发送方向的序号。
- `ack`：确认对方发送方向、表示下一步希望对方发送的序号。

因此回复报文中可以同时出现完全不同的 `seq` 与 `ack`，二者不能混为同一条序号空间。

### 3. TCP 使用累计确认

若接收方已经连续收到多段数据，可以用一个较大的 ACK 一次确认此前所有连续字节。

例如依次收到：

- `5000~5299`
- `5300~5499`

则可以直接回复 `ack=5500`。

### 4. 累计 ACK 不能跨越缺口

如果当前期望 `1000`，却先收到 `1500~1999`，由于 `1000~1499` 仍缺失，累计确认号仍停在 `ack=1000`。

只有缺口补齐、连续字节范围向后延伸后，ACK 才能继续推进。

本子考点只掌握确认语义；缺口如何触发重传放到“TCP 可靠传输：重传机制”学习。

### 5. SYN / FIN 对确认号的影响

- 普通数据按字节数占用序号空间。
- `SYN` 占用 1 个序号。
- `FIN` 占用 1 个序号。
- 普通 ACK 标志本身不额外占用序号。

例如 `seq=5000`、`200B` 数据、`FIN=1`，完整收到后下一期望序号为 `ack=5201`。

## 易错点

1. 把 `ack` 当作“最后收到的字节序号”。实际它表示“下一个期望序号”。
2. 把本方 `seq` 与本方携带的 `ack` 混在一起计算。两者分别属于两个方向。
3. 看到后续报文已到达，就让累计 ACK 跨过中间缺口。累计确认只能确认连续数据。
4. 忘记 SYN/FIN 各占一个序号，导致确认号少 1。

## 真题考法

常见题型：

- 给出 `seq` 与数据长度，求接收方确认号。
- 给出多个连续报文段，求累计 ACK。
- 制造乱序与缺口，判断 ACK 是否能继续推进。
- 双向报文中同时给出 `seq` / `ack`，判断各自含义。
