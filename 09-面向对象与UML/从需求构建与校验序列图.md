# 从需求构建与校验序列图

## 定义
从业务需求提取交互参与对象（生命线）、消息与先后顺序，并用 UML 序列图表达条件、重复、可选执行和对象生命周期；再以成功、失败、边界场景校验交互是否符合需求。

## 要点
- 先确定建模范围，再提取参与对象，生命线通常对应交互对象而不是每个 Java 方法。
- 按需求确定调用方、接收方、消息方向与时间顺序；必要时绘制同步调用、返回和执行规格。
- 对象创建用创建消息，生命线从创建处开始；不要将方法执行结束误当对象销毁。
- 多分支用 alt，可选行为用 opt，逐项处理用 loop；循环提前退出需要明确表达。
- 成功与失败路径必须互斥且符合前置约束；失败路径不能继续执行成功保存或通知。
- 将公共后续消息放在正确的控制结构外；用成功、失败、空集合等场景反向校验。

## Java/UML 完整案例
```java
OrderResult submit(OrderRequest request) {
    Order order = new Order(request);
    boolean success = true;
    for (OrderItem item : order.getItems()) {
        success = inventoryService.reserve(item);
        if (!success) break;
    }
    if (!success) return OrderResult.failed("库存不足");
    orderRepository.save(order);
    if (request.isNeedInvoice()) invoiceService.generateInvoice(order);
    notificationService.notifySuccess(order);
    return OrderResult.success(order);
}
```
- OrderService 创建 Order；loop 逐项 reserve，订单项列表为空时允许零次。
- 失败时停止 loop；循环后 alt [!success] 返回失败，不能保存、生成发票或发送成功通知。
- 成功时 alt [success] 保存一次订单；opt [needInvoice] 可选生成发票；随后无条件发送成功通知并返回成功。
- 校验场景：全部成功且需要发票、全部成功但不需要发票、第二项失败；空列表在给定代码中保持 success=true 并进入成功路径，是否允许需按业务需求另行明确。

## 易错点
- 把方法画成独立生命线，遗漏跨对象交互或颠倒调用方向。
- 先保存再检查库存，违反前置条件。
- loop 不表达失败退出，失败后仍继续成功路径。
- 把 save() 放到失败也会执行的位置；将公共成功通知误放入 opt。
- 把多步骤流程误当 loop；把逐项处理误当 alt。
- 只看 UML 符号是否正确，不用失败及边界场景验证。
