# 从需求构建与校验用例图

## 定义
根据自然语言需求识别系统边界、参与者和用例，建立关联与用例关系，再逐条核对需求的完整性和一致性。

## 要点
- 先定边界：外部人员和第三方系统可以是参与者，内部 Service、Controller、数据库通常不是。
- 从参与者业务目标提取用例，避免把 SQL、HTTP、界面步骤当成主要用例。
- 通信关联连接参与者和用例；泛化表示特殊是一种一般，空心三角指向一般元素。
- include 表示必需包含行为，箭头从基础用例指向被包含用例。
- extend 表示条件性附加行为，箭头从扩展用例指向基础用例。
- 逐条回查需求，检查遗漏、错误关系、方向及过度建模。

## Java/UML 案例
在线课程平台：注册用户查看资料；学员查询、报名、取消报名；教师发布课程；管理员审核课程。学员、教师是注册用户的特殊角色。报名必须验证资格，可选择使用优惠券；成功后通过外部短信平台通知。
- 泛化：学员、教师分别指向注册用户。
- include：报名课程指向验证报名资格。
- extend：使用优惠券指向报名课程，条件为选择有效优惠券。
- 短信平台在边界外；是否单独抽取通知用例取决于建模粒度。
```java
void enroll(User user, Course course, Coupon coupon) {
    qualification.verify(user, course);
    if (coupon != null && coupon.isValid()) couponService.apply(coupon);
    saveEnrollment(user, course);
    notification.sendSuccess(user);
}
```
代码为简化示例，不能机械地将 Java 方法调用等同于 UML 关系。

## 易错点
- 漏掉取消报名等独立业务目标。
- 把内部组件当成外部参与者。
- include、extend、泛化的箭头画反。
- 混淆必需与条件性行为。
- 擅自增加需求未说明的关系，或不检查外部平台的通信关联。
