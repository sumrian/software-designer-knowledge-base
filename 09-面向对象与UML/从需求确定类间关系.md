# 从需求确定类间关系

## 定义
在识别候选类及其成员后，根据业务语义确定 UML 类间的结构性联系、使用关系、类型层次和整体—部分约束；不能只凭单个动词或 Java 字段断言关系类型。

## 要点
- **关联 Association**：独立业务对象之间的结构性联系，例如订单长期关联所属顾客，UML 实线。
- **依赖 Dependency**：一个元素使用另一个元素，例如 CheckoutService 仅通过方法参数调用 PaymentProcessor，UML 虚线普通箭头指向被依赖者。
- **聚合 Aggregation**：整体—部分且部分可独立存在，例如部门与可调动员工；空心菱形位于整体端。若需求未明确整体—部分，普通关联也可能更合适。
- **组合 Composition**：强整体—部分与所有权/生命周期约束，例如项目任务不能脱离项目存在、项目永久删除时任务随之删除；实心菱形位于整体端。
- **泛化 Generalization**：is-a 类型关系，例如 CreditCardPayment extends PaymentMethod（父类）；实线空心三角指向父类。
- **实现 Realization**：类实现接口契约，例如 EmailSender implements MessageSender；虚线空心三角指向接口。
- 判断顺序：先识别 is-a 或接口实现，再看整体—部分及生命周期，最后区分结构性关联与单纯使用依赖；这只是推理启发式而非强制 UML 算法。

## Java / UML 示例
```java
interface MessageSender { void send(String message); }
class EmailSender implements MessageSender {
    public void send(String message) {}
}
class NotificationService {
    void notifyUser(MessageSender sender, String message) {
        sender.send(message);
    }
}
```
EmailSender 到 MessageSender 为实现；NotificationService 到 MessageSender 在给定“只通过参数使用、没有保存结构性引用”的场景下为依赖。

## 易错点
- 看到“包含”就认定为组合；需考察部分是否独立存在及整体生命周期约束。
- 看到 List/成员字段就认定聚合或组合；代码容器类型不能直接决定 UML 语义。
- 混淆泛化与实现：类继承通常为泛化，类实现接口为实现。
- 依赖与关联不是单纯以“使用时间长短”区分；关联是结构性联系，依赖是使用关系。
- 过度使用聚合；无明确整体—部分语义时普通关联可能更稳妥。

## 真题考法
- 根据需求补全关系线与箭头/菱形方向。
- 从 Java extends、implements、成员引用和方法参数推断 UML 关系。
- 结合部分对象的独立性、生命周期和所有权区分聚合与组合。
