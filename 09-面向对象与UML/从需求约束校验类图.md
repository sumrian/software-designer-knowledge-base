# 从需求约束校验类图

## 定义
将 UML 类图与业务需求逐项对照，检查是否遗漏约束、允许非法状态，或错误禁止合法状态。重点核对类与职责、关系类型、多重度、生命周期和条件性业务约束。

## 要点
- **多重度两端分别验证**：固定一个对象，数对端对象，数字写在对端。例如每个班级有 20～40 名学生、每名学生恰好一个班级，应为 `Class "1" -- "20..40" Student`。
- **合法状态与非法状态双向校验**：顾客可没有订单时，`Customer "1" -- "1..*" Order` 错误排除零订单顾客，应将 Order 端改为 `0..*`。
- **关系与数量分别校验**：订单明细依附订单的组合关系，并不自动要求至少一条明细；若订单至少一条明细，应为 `Order "1" *-- "1..*" OrderItem`。
- **条件性业务约束**：读者最多同时借 5 本，但历史借阅可无限保留，`Reader "1" -- "0..*" Loan` 配合 `{activeLoanCount <= 5}`（示意约束）比 `0..5` 更合理。
- **中间记录类**：同一学员可重复报名同一课程时，保留 Enrollment；每条 Enrollment 恰好对应一个 Student 和一个 Course；每个 Student、Course 可分别对应零到多条 Enrollment。

## Java 示例
```java
class Reader {
    private final List<Loan> loans = new ArrayList<>();
    public void borrow(Book book) {
        long activeCount = loans.stream().filter(Loan::isActive).count();
        if (activeCount >= 5) throw new IllegalStateException("超过借阅上限");
        loans.add(new Loan(book));
    }
}
```
这是简化示例，实际还需考虑库存、并发和事务；UML 约束不自动执行 Java 校验。

## 易错点
- 只检查类与关系是否存在，不检查多重度两端。
- 只检查非法状态，不检查被模型错误排除的合法状态。
- 把历史总记录数和当前有效记录数混淆。
- 以组合代替最小数量约束，或以多重度代替条件性业务规则。
- 误以为 UML 关系自动实现数据库级联删除或业务校验。

## 真题考法
- 根据需求指出错误的多重度或关系类型。
- 检查类图是否遗漏业务记录类、操作或条件性约束。
- 从对象实例和业务场景判断模型是否允许非法状态、排除合法状态。
