# 参与者识别与用例提取

## 定义
- 参与者（Actor）是与当前系统交互的外部角色，而不是具体个人、账号或 Java 类。
- 用例（Use Case）从参与者目标出发，描述系统提供的有业务意义的功能或服务。
- 分析顺序：先确定系统边界，再识别外部角色，再按角色目标提取用例，最后检查粒度、遗漏和重复。

## 要点
- 参与者可以是学员、教师、管理员等人员角色，也可以是外部支付平台、短信平台等支持性外部系统；同一人可承担多个角色。
- 主要参与者通常发起用例以实现业务目标；支持性参与者向系统提供完成目标所需的外部服务。
- 课程、订单、预约记录等是业务对象；数据库、Controller、Service、Repository 通常是内部实现组件，均不应机械地识别为参与者。
- 用例通常用动宾短语表示，例如查询课程、报名课程、发布课程、维护课程、审核课程；避免“使用系统”过粗或“执行 SQL、点击按钮”过细。
- 高层用例应围绕完整业务目标，而不是把每个内部步骤都画成同级用例。例如“账户转账”包括身份校验、余额检查、金额变更、交易记录等处理。
- 用例粒度依建模目的而定，某内部步骤在其他业务场景中可能成为独立用例。

## Java / UML 案例
在线课程系统中，学员、教师、管理员是外部参与者；查询课程、报名课程、发布课程、维护课程、审核课程是候选用例。外部短信平台可作为支持性参与者。
```java
class EnrollmentController {
    private EnrollmentService service;
    public void enroll(Long courseId) { service.enroll(courseId); }
}
class EnrollmentService {
    public void enroll(Long courseId) {
        // 检查资格与名额、保存报名记录、触发通知
    }
}
```
这些实现步骤通常共同支持高层“报名课程”用例，而不是每个 Java 方法对应一个用例。

## 易错点
- 把具体人员实例当成参与者类型。
- 将业务对象或系统内部组件误判为参与者。
- 认为只有人能成为参与者，遗漏外部支持系统。
- 将每个需求动词、SQL 或界面动作提取为独立用例。
- 用例粒度过粗或过细，忽略参与者真正的业务目标。

## 真题考法
- 从需求说明识别参与者和主要用例，补全 UML 用例图。
- 区分业务角色、业务对象与内部技术组件。
- 区分主要业务用例与内部校验/持久化步骤。
