# 用例之间的扩展关系 extend

## 定义
UML 用例扩展关系（«extend»）表示扩展用例在满足特定条件时，在基础用例的扩展点添加额外行为。基础用例即使不发生扩展，仍可独立完成其业务目标。虚线箭头从扩展用例指向被扩展的基础用例。

## 要点
- **方向**：扩展用例 ──«extend»──→ 基础用例；箭头指向被扩展者。
- **条件性**：扩展行为可由用户选择或系统根据业务条件触发，并非每次都发生。
- **基础用例完整性**：不执行扩展行为时，基础用例仍有完整业务意义。
- **扩展点**：定义在基础用例中，表示可插入扩展行为的位置；扩展条件决定是否触发。
- **与 include 区别**：include 为基础用例包含的必需行为，箭头指向被包含用例；extend 为条件性附加行为，箭头指向基础用例。
- **实现区别**：Java 中出现 if 不必然构成 UML extend；应根据业务需求和建模粒度判断。

## Java / UML 案例
在线商城：正常「结算订单」可以独立完成；若顾客选择有效优惠券，在基础用例扩展点「应用优惠」执行「使用优惠券」：
- 使用优惠券 ──«extend»──→ 结算订单
- 扩展条件：顾客选择使用有效优惠券

```java
class CheckoutService {
    Receipt checkout(Order order, Coupon coupon) {
        BigDecimal amount = order.total();
        if (coupon != null && coupon.isValid()) {
            amount = applyCoupon(amount, coupon);
        }
        return pay(order, amount);
    }
}
```
代码为简化教学示例，不能仅凭 if 分支机械推导 UML 扩展关系。

## 易错点
- 把 extend 箭头画反，让基础用例指向扩展用例。
- 误认为扩展行为必须由用户选择，忽略业务条件自动触发。
- 把扩展点误认为扩展用例：扩展点在基础用例中，表示插入位置。
- 认为扩展点一旦定义，扩展行为就必须每次执行。
- 把所有条件分支都画成 extend，或把可选行为误画成必需 include。

## 真题考法
- 根据条件性附加业务判断是否适用 extend。
- 选择或补全 extend 箭头方向、扩展条件和扩展点。
- 同时出现必需行为与条件性行为时，区分 include 和 extend。
