# 用例图基本元素与系统边界

## 定义
用例图（Use Case Diagram）是 UML 行为图，从外部使用者视角描述系统提供哪些功能、谁与功能交互，以及当前系统的建模边界。主要元素：参与者 Actor（系统外部角色）、用例 Use Case（系统对外提供的功能/服务，椭圆）、系统边界 System Boundary（界定范围的矩形）。

## 要点
- 先确定当前建模范围，再识别外部参与者和内部用例；参与者在系统边界外，用例在系统边界内。
- 参与者不一定是人，外部支付平台、短信服务、物流配送系统都可能作为外部系统参与者；当建模边界扩大并包含该系统时，其角色需要重新判断。
- 用例表达外部角色可感知的业务功能，通常以动宾短语命名，例如“查询图书”“预约挂号”“提交订单”；不直接等同于 Java Controller、Service、Repository 或 SQL。
- 参与者与用例之间的实线表示通信关联，不代表用例执行先后顺序；流程/时序可由活动图、序列图等表达。
- 案例：仅以在线商城为系统边界，顾客与第三方支付平台是外部参与者，查询商品、提交订单是内部用例；支付平台如果被包含在更大的建模范围中，就不再是该整体系统的外部参与者。

## 易错点
- 认为参与者只能是人，或根据独立部署而非系统边界判断参与者。
- 将参与者放入边界内，或将用例画在边界外。
- 把数据库表、Java Controller/Service、SQL 查询等实现细节当成面向业务的用例或外部参与者。
- 认为实线通信关联规定两个用例的执行顺序。
- 把一个 Java 方法机械对应一个用例；完整用例可能跨多个软件组件实现。

## 真题考法
- 给定需求和边界，判断参与者、用例、系统边界是否正确。
- 区分用户可感知的用例与技术实现细节。
- 判断建模边界变化后，外部系统是否仍属于参与者。
- 辨析用例图通信关联与业务执行顺序。
